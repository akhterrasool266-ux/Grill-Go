# Architecture

```
Browser ──HTML/RSC──▶ Next.js (server components, server actions, route handlers)
                         │  user's JWT (cookie)                │ service-role key (server env only)
                         ▼                                     ▼
                 Supabase Postgres  ◀── RLS + SECURITY DEFINER functions   (provisioning, webhooks, cron, public form, /platform)
                 Supabase Auth / Storage
```

## Request paths

| Path | Client used | Why |
|---|---|---|
| Pages and actions for signed-in staff/parents | **user's** Supabase client (cookie JWT) | RLS applies; a bug in a page can't read another tenant |
| Create user, reset password, platform admin, public admission, cron dispatch, webhooks | **service-role** client, after an explicit server-side check | these have no (or insufficient) user context |
| Public website (`/site/*`) | service-role, but only published rows of one active school with fixed columns | no login |

There is no Supabase client in browser bundles; login/uploads are server actions. The build was scanned: the service-role key does not appear in any client chunk.

## Server-action wrapper (`src/lib/actions.ts`)

`formAction` / `callAction` do, in order: get the signed-in context → check permission → rate-limit → validate with zod (field errors returned to the form) → run the handler with the user's client → translate any database error to a plain-language message (`src/lib/errors.ts`; unknown errors show only a reference code, details go to the server log).

## Permissions

`module.action` strings. Source of truth is `supabase/migrations/0009_permissions_bootstrap.sql`; `src/lib/auth/catalogue.ts` mirrors it for the UI and a unit test fails if they differ. Special codes: `financial.access` (see money), `campus.all` (all campuses), `classes.all` (all classes, otherwise only assigned sections), `ai.use`.
RLS policies are generated by `private.apply_rls(table, module, campus_scoped, …)`, so reads need `<module>.view`, inserts `.create`, updates `.edit`, deletes `.delete`.
Roles are per-school rows; the 18 templates are copied in by `bootstrap_school()` and are editable.

## Generic CRUD engine

About 40 simple reference tables (rooms, subjects, fee categories, vehicles, …) are described declaratively in `src/lib/resources/registry.ts` and served by `/manage/[resource]` (list, create, edit, delete, CSV export). Complex flows (fees, attendance, exams, payroll, admissions) have their own pages and RPCs.

## Money

Money tables (`fee_invoices`, `payments`, `payment_allocations`, `refunds`, `payroll*`, `journal*`, …) have **no insert/update/delete grants for clients**. All writes go through RPCs that check permission, campus, state and amounts, take row locks where needed, and write the audit trail. Invoice `balance` is a generated column per invoice, so nothing is double-counted. See `0010_rpc_fees.sql`.

## Notifications (outbox pattern)

Business events insert rows into `notification_logs` (`queued`). `/api/cron/dispatch` claims rows (`claim_notifications`, `FOR UPDATE SKIP LOCKED`), calls the provider for that channel, then `finish_notification`. If no provider has credentials the row becomes `failed: provider_not_configured`. Delivery-status webhooks update `delivered/read`. Statuses are never invented.

## Multi-tenant SaaS

`plans` (limits + feature switches), `subscriptions` (per school, with overrides), `feature_flags`, `usage_counters`. `private.plan_limit` / `private.feature_enabled` are the single enforcement point, used by `BEFORE INSERT` triggers and by the dispatcher/AI call. A suspended or archived school has no tenant context (`private.current_school_id()` returns null), so every policy fails closed.

## Internationalisation, theme, PWA

`src/lib/i18n/{en,ur}.ts`, cookie `erp_lang`; Urdu sets `dir="rtl"` and uses logical CSS properties. Theme via cookie `erp_theme`. PWA: manifest, generated icons, service worker that caches only static assets and an offline page (never authenticated HTML or API calls). Offline attendance keeps a *transient* queue in `localStorage` until it can be submitted — it is not a data store.

## Offline sync (attendance and marks)

`src/lib/offline/*` (IndexedDB outbox, snapshots, PIN gate), `POST /api/sync`, and the functions `sync_attendance` / `sync_marks` (migration 0021). The server is the only source of truth; the phone holds a read-only snapshot and a queue of operations.

- **Idempotency:** each queued operation has a client-generated UUID stored in `sync_receipts` with its result; a replay returns the stored result and changes nothing. Receipts are bound to the user and not readable by clients.
- **No silent overwrite:** attendance only inserts missing rows; marks use compare-and-set against the value the phone saw. Differences are returned as `conflicts` and shown to the user.
- **Bounded:** attendance can be back-filled 3 days; locked/published exams reject.
- **Why a JSON route, not a server action:** a queued item must still work after a redeploy changed server-action ids.
- **Why only these two:** both are per-student rows that are naturally last-writer-visible and low-risk. Fees/payroll are money and must not be recorded on devices that can't see each other.
- **Service worker:** caches only the data-free `/offline-work` shell and static assets; never signed-in HTML.
